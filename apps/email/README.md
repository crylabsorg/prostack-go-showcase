# Email service

Run `docker compose -f devops/docker-compose.yaml up -d postgres mongo nats kafka jaeger`, apply migrations with `make migrate-up-user`, then run `make run-user` and `make run-email` from the repository root. The default `EMAIL_PROVIDER: fake` logs welcome emails without sending them.

For real delivery, set `EMAIL_PROVIDER=mailgun`, `EMAIL_FROM`, `MAILGUN_DOMAIN`, and `MAILGUN_API_KEY` in the email process environment. Set `MAILGUN_BASE_URL=https://api.eu.mailgun.net` for an EU region domain; the default is `https://api.mailgun.net`.

User creation commits the user and `user.created` event together. The user service retries publication to both JetStream and Kafka, and the email service subscribes to the event and acknowledges it only after the provider accepts it. MongoDB stores one welcome delivery per user in `email.welcome_deliveries`, using the user ID as its unique `_id`. Both consumers reserve the delivery in a transaction before sending, record `sent_at`, and commit before acknowledging the event. Concurrent reservations conflict and are retried by the broker; committed deliveries are skipped. Provider failures roll back the reservation. A crash after provider acceptance but before MongoDB commits can still cause a repeat. Transaction callbacks are never automatically retried.

User requests and events use `first_name` and `last_name`. Each `user_outbox` message has its own `id`, with `user_id` referencing the user. Publication sets `processed_at` after both brokers acknowledge the message; processed rows are retained and excluded from subsequent batches.

Both adapters implement `ps_event.Publisher`; `ps_event.Fanout` attempts both for each outbox message. Kafka uses topic `user.created` and the outbox event ID as the record key; NATS uses the same ID in `Nats-Msg-Id`. If either broker fails, the outbox record remains pending and the next attempt republishes to both. Kafka consumers must tolerate duplicates even with an idempotent producer; NATS deduplication is limited to its configured window.

The email service starts a NATS consumer when `NATS_URL` is nonempty and a Kafka consumer when `KAFKA_BROKERS` is nonempty. At least one must be configured; both can run together. The default config enables both NATS and Kafka. `MONGO_URI` configures the email database and must point to a replica set (provided by the local Compose setup). For Kafka only, set `NATS_URL: ""` and `KAFKA_BROKERS: [localhost:9092]` in `apps/email/config.local.yaml`. Kafka brokers can also be supplied through `KAFKA_BROKERS=localhost:9092` (comma-separated for multiple brokers). Kafka uses consumer group `email-sender` and commits offsets after successful delivery. Provider failures leave the offset uncommitted and restart the consumer after five seconds. Malformed JSON is logged and committed, matching NATS termination. Both consumers share MongoDB delivery history, so replaying an already committed welcome delivery through either broker does not send it again. Keep this history to preserve deduplication across restarts and source changes.

Kafka processes batches of up to 50 records concurrently, including records from the same partition. Handlers must be safe to call concurrently; message processing can finish out of order. Offset commits remain ordered within each partition and stop at the first processing or commit failure. Later records in that partition may have completed their work but are retried after restart, so delivery remains at least once. Draining stops polling and waits for the active batch, including its commits, before closing the client.

Kafka producer and consumer spans use the existing OTEL exporter configuration. W3C trace context and baggage travel in record headers. The outbox publication links to the stored request trace; consumer spans link to the producer span. Inspect these links in Jaeger at <http://localhost:16686>. Kafka processing and commit failures mark the span as an error.
